## 2. 무엇을 만드나 (30초)

한 문장으로 말씀드리면, **AI가 먼저 판정하고, 애매한 웨이퍼만 사람이 확정하는 웹 서비스**입니다.

입력은 WM-811K 데이터처럼 전기 검사 결과를 0, 1, 2로 적은 웨이퍼 맵입니다. 모델은 CoAtNet-0이고 정상과 결함 8종, 모두 9개 클래스로 분류합니다. 판단 근거는 Grad-CAM 히트맵으로 보여 줍니다.

핵심은 세 번째 칸입니다. 확신이 낮은 웨이퍼는 사람에게 넘기고, 사람이 확정한 결과는 다시 학습 데이터가 됩니다. 이번 학기 목표는 이것을 **다른 사람이 실제로 쓸 수 있는 서비스**로 만드는 것이었습니다.

## 3. 지금 어디까지 왔나 (40초)

지금 상태를 숫자 다섯 개로 요약했습니다.

학습에 쓰지 않은 데이터 17,504건에서 테스트 정확도 **97.74%**, macro-F1 0.891입니다. 자동 테스트는 235건이고 코드를 올릴 때마다 돌아갑니다. 운영 서버에서 실제 웨이퍼로 기능 65개 항목을 점검해 모두 통과했습니다. API는 28개로, 설계했던 9개를 모두 구현했습니다.

아래 비교가 이번 한 달의 요약입니다. 10월 1일에는 서버가 없었고, 정확도도 학습과 섞인 검증 값뿐이었습니다. 지금은 **HTTPS 주소로 누구나 접속하는 서비스**가 돌고 있습니다.

## 5. 시스템 구성 (45초)

구성은 단순합니다. 브라우저의 React 화면이 Nginx를 거쳐 FastAPI 서버에 요청하고, 기록은 PostgreSQL에 남습니다. 이 세 컨테이너가 Azure 가상 머신 한 대에서 Docker Compose로 돌아갑니다.

두 가지를 짚겠습니다. 첫째, 추론은 ONNX Runtime으로 해서 **GPU 없는 서버에서도 빠릅니다**. Grad-CAM이 필요할 때만 PyTorch 모델을 올립니다. 둘째, 모델 파일을 이미지 밖에 두어서 재학습한 모델로 바꿀 때 다시 빌드하지 않습니다.

(GitHub Actions가 push할 때마다 테스트 235건과 실제 Docker 배포 절차를 돌려서, 배포 구성이 틀어지면 바로 알 수 있습니다.)

## 6. 웨이퍼 한 장이 지나가는 길 (45초)

웨이퍼 한 장이 들어오면 네 단계를 거칩니다.

먼저 형식과 값을 검사해서, 틀리면 이유와 함께 거절합니다. 전처리는 **학습 때와 비트 단위로 같게** 맞췄고, 1학기 검증 정확도를 서버에서 그대로 재현해 확인했습니다. 모델이 9개 클래스 확률을 내면, 판정 로직이 Near-full 밀도 규칙을 먼저 보고 확신도가 0.80보다 낮으면 사람에게 넘깁니다.

결과적으로 테스트 셋 기준 **96.42%는 자동으로 나가고, 3.58%가 검토 대기열**로 갑니다. 사람이 검토한 건이 500건 쌓이면 재학습 작업이 자동으로 생깁니다.

## 7. 재학습 (50초)

여기가 이번 발표에서 가장 중요한 부분입니다.

10월 발표의 96.45%는 **검증 정확도**였고, 학습에 쓴 로트가 검증에도 섞여 있었습니다. 그래서 로트 단위로 학습 80, 검증 10, 테스트 10으로 다시 나누고 처음부터 새로 학습했습니다.

학습에 전혀 쓰지 않은 테스트 셋에서 **97.74%**가 나왔습니다. 숫자가 올라 보이지만 성격이 다릅니다. **이번 값이 더 엄격한 값**입니다. 실제 분포에서 macro-F1 0.891, 클래스를 고르게 뽑은 표본에서 0.918입니다.

약한 클래스는 Loc, Scratch, Donut입니다. Donut은 테스트 표본이 32건뿐이라 수치가 흔들릴 수 있습니다.

(같은 테스트 셋에서 1학기 모델은 98.19%가 나오지만, 그 샘플을 학습에 썼기 때문에 비교에서 뺐습니다.)

## 8. 판정 로직의 효과 (50초)

정확도만큼 중요한 것은 **몇 장이 사람에게 가고, 몇 장이 틀린 채 나가느냐**입니다.

테스트 셋에서 96.42%가 사람 검토 없이 나갔고, 그 안의 정확도는 99.23%입니다. 검토로 간 3.58% 중 AI가 맞힌 것은 57.7%입니다. 애매한 것을 제대로 골라내고 있다는 뜻입니다. 결함을 정상으로 내보낸 것은 19건이고, 주로 Edge-Loc과 Loc입니다.

측정하면서 두 가지를 알게 됐습니다. 하나, 1학기 발표의 "95.05% 통과, 1.40% 오류"를 같은 조건으로 다시 재니 94.65%, 1.51%로 **1학기 측정이 맞았습니다**. 둘, 확신도가 0.90에서 0.92 사이에 몰려 있어서, 임계값을 그 위로 올리면 거의 모든 웨이퍼가 검토로 갑니다. 그래서 **설정 화면이 모델별 상한을 알도록** 고쳤습니다.

## 9. Grad-CAM (35초)

검토자가 AI 판정을 믿으려면 근거가 보여야 합니다.

Grad-CAM은 모델이 웨이퍼의 어느 부분을 보고 판단했는지 히트맵으로 보여 줍니다. 그림처럼 가운데, 도넛, 가장자리 링, 스크래치 패턴에서 **히트맵이 실제 결함 자리에 뜨는지 자동 테스트로 확인**하고 있습니다.

계산이 무거워서 상세 화면을 열 때만 만들고, 한 번 만든 것은 저장해 둡니다. 처음 1초, 그다음부터는 0.55초입니다.

## 10. 배포 (45초)

이 주소는 지금 열립니다.

서버는 학교 지원을 기다리는 대신 **Azure 학생 크레딧**으로 확보했습니다. 카드 등록 없이 1월 중순까지 운영할 수 있습니다. 한국 리전은 학생 구독에서 막혀 있어 가장 가까운 홍콩 리전을 썼습니다.

실측으로 예측 한 건은 0.17초에서 0.34초, 5건을 동시에 올려도 0.7초입니다. 로그인 쿠키를 HTTPS에서만 보내도록 해 두었기 때문에 인증서를 받아 HTTPS로 운영합니다.

(배포 당일 막힌 것은 리전 제한 하나뿐이었습니다. 같은 배포 절차를 CI가 매번 미리 돌려 보기 때문입니다.)

## 12. 로그인 보호 (50초)

외부에 열린 서비스라서 로그인 보안을 **OWASP 인증 체크리스트**로 점검했습니다.

왼쪽은 처음부터 있던 것입니다. 없는 사번과 틀린 비밀번호에 같은 응답을 주어 계정 존재를 숨기고, 비밀번호는 bcrypt로 저장하고, 토큰은 자바스크립트가 읽지 못하는 쿠키에 담습니다.

비어 있던 것은 **무차별 대입 방어와 세션 무효화**였습니다. 그래서 5번 연속 틀리면 잠그고, IP당 요청 수를 제한했습니다. 로그아웃하거나 비밀번호를 바꾸면 이전 로그인이 실제로 끊기게 했고, 임시 비밀번호로 들어오면 바꾸기 전까지 다른 기능을 막습니다.

(잠금을 영구로 두지 않은 이유는, 공격자가 남의 사번을 일부러 잠가 업무를 막을 수 있기 때문입니다.)

## 예상 질문과 답

**97.74%가 96.45%보다 높은데 왜 더 엄격한 값인가요?**
96.45%는 학습에 쓴 로트가 섞인 검증 값입니다. 97.74%는 한 번도 보지 않은 로트로 잰 테스트 값입니다. 같은 테스트 셋에서 1학기 모델은 98.19%가 나오지만, 그 샘플을 학습에 썼기 때문에 비교하지 않았습니다.

**실물 웨이퍼 사진도 분류할 수 있나요?**
WM-811K는 사진이 아니라 전기 검사 결과인 0, 1, 2 맵입니다. 그 맵을 그린 그림은 받지만, 카메라로 찍은 사진은 다른 과제입니다.

**결함을 정상으로 내보낸 19건은 어떻게 줄이나요?**
대부분 Edge-Loc과 Loc입니다. 임계값을 올리면 줄지만 검토량이 급격히 늘어서, 지금은 검토 결과가 쌓이면 재학습으로 줄이는 쪽을 택했습니다.

**서버가 멈추면 어떻게 되나요?**
세 컨테이너 모두 자동으로 다시 시작하고 상태 검사로 감시합니다. 크레딧이 끝나면 멈출 뿐 요금이 청구되지 않습니다. 노트북에서 같은 화면을 띄우는 예비 구성도 있습니다.

**회원가입을 왜 승인제로 했나요?**
공장 품질 시스템이라 주소만 알면 누구나 들어오면 안 됩니다. 승인 전에 로그인하면 비밀번호까지 맞을 때만 "승인 대기"라고 알려 주므로, 사번만으로는 계정이 있는지 알 수 없습니다.

**재학습을 실제로 돌려 봤나요?**
네. 지금 운영 중인 모델이 그 결과입니다. 데이터 내려받기, Colab 학습, 승격 판정, 교체까지 끝까지 실행했습니다.

**테스트 235건은 무엇을 확인하나요?**
전처리가 학습과 똑같은지, 판정 경계값, 인증과 권한, DB 마이그레이션, Grad-CAM 위치, 배포 구성까지 봅니다. SQLite와 PostgreSQL 양쪽에서 돌립니다.

**보안은 어디까지 봤나요?**
OWASP 인증 체크리스트로 점검했습니다. 계정 존재 숨기기, bcrypt, 쿠키 보호, HTTPS와 보안 헤더는 처음부터 있었습니다. 이번에 연속 실패 잠금, IP 요청 제한, 로그아웃과 비밀번호 변경 시 세션 무효화, 임시 비밀번호 강제 변경, 비밀번호 규칙, 감사 로그를 더했습니다.
